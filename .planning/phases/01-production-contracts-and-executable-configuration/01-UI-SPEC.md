# Phase 1 — UI Design Contract

> Visual and interaction contract for the protected preview-only approval review report. Generated by gsd-ui-researcher for validation by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | Existing repository-local plain CSS; no shadcn initialization and no new design-system dependency |
| Preset | Not applicable |
| Component library | Existing server-compatible primitives in `src/components/ui/Shared.tsx`; no external component library |
| Icon library | None; use text labels and existing CSS shapes only when decorative |
| Font | Arial, Helvetica, sans-serif via the existing global font stack |

Source: `AGENTS.md`, `01-RESEARCH.md`, `src/app/globals.css`, and `src/components/ui/Shared.tsx`. The existing Hino-compatible red, white, and charcoal system is locked. This phase does not redesign public pages.

### Surface Boundary

- Add exactly one separate, protected, preview-only approval review report. It is read-only and server-rendered.
- Public pages in protected preview must use the same eligible-content selectors and omission behavior as production. Do not render reviewer badges, approval labels, provisional facts, developer placeholders, missing-content callouts, or diagnostic copy inside public-looking pages.
- The report is not part of the public site shell: omit it from the primary navigation, footer links, sticky mobile actions, breadcrumbs, internal-link registries, metadata discovery, structured data, and sitemap.
- In production, the equivalent report URL must return the shared 404 response. It must never render a login prompt, report title, redirect, or partial report that reveals the route exists.
- In preview, the report must declare `noindex`, `nofollow`, and `noarchive` and rely on platform deployment protection as the access boundary. No application authentication UI is introduced.
- The report consumes only an allow-listed, redacted DTO. It must not display secret values, raw environment values, personal names, contact details, submitted lead data, credentials, tokens, evidence bodies, signatures, signed URLs, provider endpoints, or sensitive document locations.

## Spacing Scale

Declared values for new report-specific styles; all are multiples of 4 and align with the existing CSS rhythm:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Status-label internal gaps and definition-term separation |
| sm | 8px | Inline metadata, compact cell spacing, badge padding |
| md | 16px | Default cell/card padding and control gaps |
| lg | 24px | Report section padding and stacked-card gaps |
| xl | 32px | Header-to-summary and subsection breaks |
| 2xl | 48px | Major section breaks on compact screens |
| 3xl | 64px | Major section breaks on desktop |

Exceptions: interactive targets remain at least 44px square; any button-like link uses the existing 48px minimum height. The existing 12px card radius and 5px compact-control radius remain unchanged.

## Typography

The report declares exactly four sizes and two weights. Do not introduce additional report-specific font sizes or weights.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label / table header | 14px | 700 | 1.4 |
| Section heading | 22px | 700 | 1.2 |
| Page title | 32px at every breakpoint | 700 | 1.2 |

Use sentence case for headings, table headings, labels, and status text. Keep line length at 72 characters for explanatory prose. IDs, dates, and evidence-reference codes may use the inherited font stack; do not add a monospace font or shrink them below 14px.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`--paper`) | Page background, primary report surface, table/card rows |
| Secondary (30%) | `#f3f4f4` (`--surface`) with `#17191b` (`--ink`) text | Report header band, summary panels, alternating groups, neutral status surfaces |
| Accent (10%) | `#d71920` (`--brand`) | Eyebrow, current-section marker, primary anchor CTA, left rule on production-blocker summary only |
| Destructive | `#a40d14` | Blocked, expired, invalidated, and generation-error text/borders only |

Accent reserved for: the report eyebrow, the “Review production blockers” anchor, keyboard-focus-compatible active markers, and the production-blocker summary rule. Do not use red as decoration on every card, row, heading, or link.

Supporting existing semantic tokens may be used only with explicit text labels: `#117a46` for “Approved / current” and `#a45e00` for “Review due / evidence incomplete.” Every state must remain understandable in monochrome; color never replaces the status word, count, or explanation. Body text uses `#17191b`; secondary copy uses `#62676b`; borders use `#d9dcde`. Preserve the existing blue `:focus-visible` outline.

## Information Architecture

Render the report in this fixed order:

1. **Protected preview header** — eyebrow “Protected preview,” H1 “Production approval review,” one-sentence purpose, generated timestamp, deployment target label, and configuration fingerprint/reference when available and non-sensitive.
2. **Readiness summary** — overall text status, blocker count, missing-approval count, due/expired count, ineligible-route count, and environment-isolation result. The first summary item states either “Production blocked” or “Ready for release-owner review”; it never says “Production ready” because final promotion remains a human approval.
3. **Production blockers** — highest-priority items first, grouped by blocker code. Each item shows public-safe label, affected surface, responsible lane, next required action, and opaque evidence-reference status.
4. **Approvals and evidence** — all required decision/claim records grouped by approval lane: Sales; Aftersales; Privacy/legal; Brand/content; Technical release. Each record shows ID, label, approval status, approver role, evidence-reference status, approved date when present, next-review/expiry date, and affected surfaces.
5. **Route eligibility** — every governed route with one of: “Eligible,” “Eligible in reduced form,” or “Withheld.” Show the four minimum-viable-truth checks—identity, purpose, request semantics, contact action—and a concise reason for any failing check.
6. **Environment isolation** — development, preview, and production rows for origin class, lead profile class, analytics profile class, crawl policy, review-report availability, and overall pass/block result. Display classifications such as “unique preview origin” or “approved production profile,” never raw values.
7. **Report limitations** — state that automated checks verify repository/configuration contracts, while evidence authority, document access, and final stakeholder approval still require human review.

The report must not include approval mutation controls, provider selection controls, editable inputs, file uploads, secret reveal/copy controls, or a “promote” action.

## Component Contract

| Component | Required contract |
|-----------|-------------------|
| Report container | Reuse `.container`; maximum width remains `1180px`. Use a single `<main id="main-content">`. |
| Report header | Compact charcoal or neutral-surface band, not the marketing `PageHero`; no public navigation or mobile conversion bar. |
| Summary grid | Six summary cards at desktop, three at medium widths, one per row on small screens. Each card includes label, numeric/text value, and one-line interpretation. |
| Status label | Text-first inline label with status word and optional CSS dot. Dot is `aria-hidden`; status text is never abbreviated. |
| Blocker list | Semantic ordered or unordered list. Each item uses a 4px destructive left rule only when blocking production. |
| Approval groups | One `<section>` per lane with heading and item count. Desktop may use a table; mobile must use equivalent stacked definition cards without losing labels. |
| Route eligibility | Table/card view containing route label and path only when the path is non-sensitive, overall eligibility, four truth checks, and reason/next action. |
| Isolation matrix | Table/card view with a caption and explicit pass/block text for each deployment target. No raw URLs, identifiers, or environment values. |
| Evidence reference | Show only status (“Present,” “Missing,” “Broken shape,” “Review required”), external system/type label if approved for disclosure, and opaque reference ID. Render as plain text unless the destination is explicitly approved and access-controlled. |
| Section navigation | A short in-page list of anchor links after the header. Links target the six report sections and use native scrolling; no JavaScript state. |

Use scoped report classes such as `.approval-report`, `.review-summary`, and `.status-label`. Do not change the meaning or presentation of existing shared public classes to accommodate the report.

## Responsive Contract

- **≥1061px:** Use the full `1180px` container. Summary uses up to six equal columns. Data tables use stable columns, visible captions, and natural row wrapping.
- **721–1060px:** Summary uses three columns. Approval and route tables may reduce secondary columns, but omitted data must appear in an adjacent definition list or details block in the same DOM; do not hide required status or ownership information.
- **≤720px:** Use the existing `calc(100% - 2rem)` container. Summary becomes one column. Replace wide tables with stacked cards/definition lists; do not require horizontal page scrolling. Each card order is label/status, owner lane, dates, evidence, affected surfaces, then next action/reason.
- Long record IDs and opaque evidence references use `overflow-wrap: anywhere`. Dates use an unambiguous human format such as “18 Aug 2026”; machine timestamps may appear in accessible `<time datetime>` elements.
- The report never renders the public sticky mobile action bar. No content may be obscured by fixed positioning.

## Interaction and State Contract

- The report is usable with HTML and CSS alone. Do not add a client component solely for filtering, sorting, tabs, accordions, tooltips, or copy-to-clipboard.
- In-page section links are the only primary interaction. “Review production blockers” targets the blockers heading; every target receives visible focus and `scroll-margin-top` sufficient for the sticky public header only if that header is intentionally retained. Prefer omitting the public header.
- Native tables are not sortable. Their source order is deterministic: production blockers first, then status severity (`invalidated`, `expired`, `pending`, `approved`), then review date, then stable record ID.
- Evidence references are not fetched or expanded by the browser. The server report builder provides only redacted display fields.
- A record exactly at its review boundary is “Review due” and ineligible where the governance contract requires current approval. Expired or invalidated records are never visually conflated with pending records.
- When a route is eligible in reduced form, list the approved retained elements and withheld categories. Do not preview withheld wording.
- When the environment matrix fails, place an error summary immediately after the H1 and identify safe variable names or policy codes only; never echo their values.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Report eyebrow | Protected preview |
| Report title | Production approval review |
| Intro | Review redacted approval, evidence, route eligibility, and environment-isolation status before this deployment can be considered for production promotion. |
| Primary CTA | Review production blockers |
| Blocked summary | Production blocked — resolve every listed blocker and record the required approval evidence before promotion. |
| Clear summary | Ready for release-owner review — automated contract checks passed; final human approval is still required. |
| Empty state heading | No production blockers found |
| Empty state body | Automated checks found no unresolved blockers in this report. The release owner must still verify external evidence and complete the promotion checklist. |
| Report generation error | Approval report unavailable. Do not promote this deployment. Re-run the governance and configuration checks, then ask the technical release owner to review the failure. |
| No records in a lane | No governed records are registered for this approval lane. Confirm that this is intentional before release review. |
| Destructive confirmation | Not applicable — this report exposes no destructive or mutating actions. |

Copy must be factual and operational. Never use celebratory success language, imply approval from a green check alone, show unapproved business values, name an unapproved provider, or turn proposed thresholds/cadences into approved policy.

## Accessibility Contract

- Meet WCAG 2.2 AA practices already required by `AGENTS.md`. Use one H1, ordered H2 sections, and H3 only for groups within a section; do not skip heading levels.
- Provide a “Skip to report content” link as the first focusable element if any shell content precedes `<main>`.
- Every table has a visible `<caption>`, `<th scope="col">` column headers, and `<th scope="row">` row headers where applicable. Mobile card alternatives retain explicit `<dt>/<dd>` labels.
- Status changes are not live updates because the page is server-rendered. Do not add `aria-live` or `role="alert"` to static status summaries. The report generation error may use `role="alert"` only if it appears after client-side navigation; otherwise use a heading and normal document flow.
- All links and any controls have a minimum 44×44px target and a visible `:focus-visible` outline. Anchor link text must describe the target section.
- Color, position, and icons are never the sole means of conveying status. Every semantic color is paired with the exact status phrase and, where needed, a reason.
- Respect `prefers-reduced-motion`; use no animation, auto-refresh, pulsing badges, or animated progress indicators.
- At 200% zoom and 320 CSS px viewport width, content reflows without loss, overlap, clipped status text, or two-dimensional scrolling.

## Discovery and Security Assertions

The executor and checker must be able to prove all of the following:

- Preview public pages contain no review-report labels, provisional values, or inline approval diagnostics.
- The report route is absent from header/footer/mobile navigation, internal-link registries, sitemap, metadata alternates, structured data, and public search surfaces.
- Production requests to the report route return 404 and render no report DTO.
- Preview report metadata blocks indexing, following, and archiving; platform preview protection remains required.
- Rendered HTML and serialized React data contain no secret-like keys, raw `process.env`, PII, signed evidence URLs, provider endpoints, or evidence document bodies.
- The environment matrix shows classes/statuses only, not raw origins, IDs, destinations, analytics identifiers, or credentials.
